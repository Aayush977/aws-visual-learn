## The problem

Brightwell's application instances sit in private subnets, exactly as Project 3 laid out. Which
raises an awkward operational question: when something breaks at 2am, how does an engineer
actually get a shell on one?

The traditional answer is a **bastion host** — sometimes called a jump box. A small EC2 instance
in a public subnet, with port 22 open to the internet (or, if somebody is being careful, to the
office IP range). You SSH into that, then SSH onward to the private instance.

It works. It has also quietly created four separate problems:

- **An open inbound port on the internet.** Even restricted to an IP range, it is a permanent
  door, and it is scanned continuously.
- **An SSH key.** Which means a private key file, which means it is on somebody's laptop, and
  probably on three laptops, and quite possibly in a password manager shared with a contractor
  who left in March.
- **Another server to look after.** The bastion is an EC2 instance: it needs patching,
  monitoring and paying for, and it does no useful work.
- **No audit trail worth the name.** You can see that *someone* connected from an IP address.
  Which human being that was, and what they typed, is not recorded anywhere useful.

**Session Manager** removes all four, and the mechanism is worth understanding rather than
memorising.

## Why the direction of the connection is the whole idea

Almost everything good about Session Manager follows from one fact: **the agent connects
outward, and the session is relayed back down that connection.**

Nothing ever initiates a connection *to* your instance. So there is no inbound rule to write, no
port to leave open, and nothing for an internet-wide scanner to find. The instance can sit in a
private subnet with a security group that permits **no inbound traffic whatsoever** and still be
administrable from a browser.

Compare that to the bastion, where security depends on an open port being defended well. Removing
the port entirely is a stronger guarantee than defending it carefully.

## The three things that must be true

The lab is useful here because it is specific about what actually has to be in place. When
Session Manager does not work, it is essentially always one of these — and the failure is
usually **silence** rather than an error.

1. **The SSM Agent is running.** Preinstalled on Amazon Linux 2 and 2023, recent Ubuntu and
   Windows Server AMIs. On anything else you install it yourself.
2. **The instance has an IAM role** with the `AmazonSSMManagedInstanceCore` managed policy. This
   is what lets the agent register with Systems Manager. No role, no instance in the list.
3. **The agent can reach the service.** Via NAT, or — for a genuinely private subnet — via the
   three interface endpoints. This is Project 7's mechanism doing real work.

<Callout type="gotcha" title="Why three endpoints, and what happens with two">
<code>ssm</code> is the control channel, <code>ssmmessages</code> carries the actual session
data, and <code>ec2messages</code> handles instance messaging. They are separate services and
each needs its own interface endpoint.

Create only the first and the instance registers fine and appears in the console — but starting
a session hangs, because the data channel has nowhere to go. **A partially-configured setup
looks more broken than a completely unconfigured one**, which is why this catches people. If
sessions fail but the instance is visible, check <code>ssmmessages</code> first.
</Callout>

<Callout type="cost">
Session Manager itself is <strong>free</strong>, and it deletes a bastion instance from your
bill. Against that, three interface endpoints are charged per hour per Availability Zone — so in
a small VPC that already has a NAT gateway, using NAT is cheaper. In a properly private VPC with
no NAT at all, the endpoints are the only option and the comparison is with the bastion you no
longer run.
</Callout>

## What this replaces beyond SSH

Once Systems Manager is set up, several other awkward jobs stop needing a shell at all — worth
knowing because they show up as exam distractors:

- **Patch Manager** applies operating-system patches on a schedule and reports compliance, so
  patching stops being something a person does over SSH.
- **Run Command** executes a command across a fleet at once, with the results recorded, instead
  of logging into forty machines.
- **Parameter Store** holds configuration and secrets, so they need not be baked into an AMI or
  copied onto a disk.
- **Fleet Manager** gives a file browser and process list in the console — often enough to
  diagnose a problem without a shell at all.

There is a wider habit worth taking from this one.

The bastion host was not a bad design. It was a correct design for a period when the only way to
reach a machine was to connect to it, so the work went into defending that connection well —
restricted ranges, key rotation, hardened jump boxes.

Session Manager did not defend the door better. It **removed the requirement for a door**, and
the entire class of problems went with it. When you meet an architecture that spends a lot of
effort protecting something, it is always worth asking whether the thing still needs to exist.
