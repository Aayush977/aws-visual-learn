## "So was AWS hacked?"

In 2019 a large American bank disclosed that the personal data of roughly 106 million credit
card customers and applicants had been taken. Names, addresses, credit scores, and some
hundreds of thousands of national insurance numbers.

The obvious question, asked in a lot of board meetings that month, was whether AWS had been
broken into.

It had not. Every AWS control worked exactly as designed. The attacker did not touch a
datacentre, a hypervisor or a disk. What actually happened, in outline: a misconfigured web
application firewall let an attacker make the bank's own server fetch a URL on its behalf; that
URL was the instance metadata service, which handed over the credentials of the role attached
to the instance; and that role was permitted to list and read the buckets holding the data.

Read that chain again and count the AWS failures. **There are none.** A firewall rule, a role's
permissions, a bucket's contents — every link belonged to the customer, and every link sat on
the customer's side of a line that was published, in advance, in plain English, and that
almost nobody in that story had sat down and read.

That line is this lesson.

## Whose fault is what

Almost every AWS security breach you read about follows the same shape. It is not AWS being
broken into. It is a customer leaving a bucket public, an access key in a public repository, a
database open to the whole internet, or a role that could read far more than its job required.
The Shared Responsibility Model is AWS writing down, in advance, exactly whose fault each of
those is.

The one-line version: **AWS is responsible for security *of* the cloud. You are
responsible for security *in* the cloud.**

## The line moves with the service model

This is the part people skip, and it is the part the exam actually tests. "Who patches
the operating system?" has no single answer — it depends entirely on which service you
are using.

| You are using | Who patches the OS | Who patches the database engine | Who scales it |
| --- | --- | --- | --- |
| **EC2** (IaaS) | You | You | You |
| **RDS** (PaaS) | AWS | AWS applies it, you choose the window | You pick the size; AWS does the work |
| **Lambda** (FaaS) | AWS | n/a | AWS, automatically |
| **S3** (managed storage) | AWS | n/a | AWS, invisibly |

Read that table top to bottom: as you move to more managed services, you hand more
responsibility to AWS — and give up more control in exchange.

<Callout type="gotcha">
Moving to a managed service never transfers responsibility for **your data or your
access controls**. AWS patches RDS for you, but if you put the database in a public
subnet with an open security group, that is still on you. Amazon S3 encrypts every
object at rest by default, but making the bucket public is a customer action.
</Callout>

Go back to the bank. Walk their breach along the line one more time, and notice that the model
does not merely assign blame after the event — **it tells you where to look before one.**

A firewall rule is yours. A role's permissions are yours. What is in a bucket is yours. Three
questions, all answerable on a quiet Tuesday, none of which require trusting AWS about anything.

That is what the model is actually for. Not a disclaimer, but a very short list of the things
nobody else is going to check for you.
