## "Just buy a bigger server"

Two weeks after the television Tuesday, Kettle & Fox got a quote for a bigger server. Twice the
cores, twice the memory, £11,000, six weeks' lead time. It would have survived that Tuesday
with room to spare.

It would also have been **one server**. One power supply, one disk controller, one building. A
bigger thing to lose, in the same single room, still six weeks away from every decision.

They asked a contractor what the alternative looked like. Her answer was not "a bigger server"
and it was not one change — it was four, in a strict order, and she was blunt that doing them
out of order buys you nothing:

> Two of something. Something in front deciding where traffic goes. Something that adds and
> removes copies on its own. And — the one everybody skips — nothing important living inside
> any single copy.

Most systems begin exactly where Kettle & Fox began: one server. It works, until the day it
does not, and then it fails completely — because there is nothing else to take over and no way
to grow except by buying a bigger one.

Here are the four changes. Play it through, then read the section for each.

## Up or out

**Scaling up** (vertical) means replacing the instance with a bigger one. It is simple, it
requires no application changes, and it has two hard limits: there is a largest instance type,
and you still have exactly one of them. Rebooting into a new size means downtime. *This is the
£11,000 quote. It solves the Tuesday and none of the other days.*

**Scaling out** (horizontal) means running more instances. There is no ceiling worth worrying
about, a failure removes a fraction of capacity rather than all of it, and you can add and
remove capacity without downtime. It requires your application to tolerate having copies of
itself — which is the statelessness problem below.

<Callout type="exam">
When a question asks for <strong>high availability</strong>, the answer almost always involves
scaling <em>out</em> across <strong>multiple Availability Zones</strong>. A bigger instance is
never a high-availability answer, no matter how big — it is still one instance in one zone.
</Callout>

Two related words the exam distinguishes:

- **Scalability** — the system *can* handle more load, by adding resources.
- **Elasticity** — it adds and removes them **automatically**, matching demand as it changes.
  Elasticity is what saves money, because it includes shrinking.

## The load balancer, and what health checks really buy

An **Elastic Load Balancer** takes incoming requests and spreads them across registered
targets. The part that matters for availability is the **health check**: the load balancer
polls each target on a path you choose, and stops sending traffic to anything that fails.

That is what turns a dead instance into a non-event. Nobody is paged, no user sees an error,
and if an Auto Scaling group is watching, a replacement appears within minutes.

To enable multi-AZ properly you must **enable the load balancer in each Availability Zone** you
want to use. A load balancer that only has a presence in one zone cannot save you from losing
that zone.

## Auto Scaling groups

An **Auto Scaling group (ASG)** maintains a fleet. You give it:

- A **launch template** — the AMI, instance type, security groups and user data for any new
  instance it creates.
- **Minimum, desired and maximum** counts. It will never go below the minimum or above the
  maximum, and it works to keep the desired number healthy and running.
- A list of **subnets across several Availability Zones**, which it balances instances across.
- **Health checks** — its own, or (better) the load balancer's, so an instance that is running
  but not serving traffic still gets replaced.

Even with no scaling policy at all, an ASG with min = desired = 2 is worth having: it means
"there will always be two healthy instances", and it will rebuild them if they die.

Scaling policies decide when the number changes:

<Callout type="gotcha">
Scaling out takes minutes — an instance must boot, pass health checks and warm up. If your
traffic spikes in seconds, reactive scaling arrives late and users see the spike anyway. That
is what <strong>scheduled</strong> and <strong>predictive</strong> scaling are for, and it is
why questions about a known daily peak want scheduled scaling rather than target tracking.
</Callout>

## Statelessness: the precondition for all of it

If any user's data lives in one instance's memory or on its local disk, then instances are not
interchangeable, and everything above collapses. Terminating an instance logs people out;
scaling out sends users to a server that has never heard of them.

Where state actually goes:

| State | Put it in |
| --- | --- |
| Session data, shopping baskets | **DynamoDB** (with TTL) or **ElastiCache for Redis** |
| Uploaded files | **Amazon S3** |
| Shared files a filesystem must see | **Amazon EFS** |
| The application's data | **RDS**, **Aurora** or **DynamoDB** |
| Nothing at all | The instance's local disk |

Load balancers do offer **sticky sessions**, which pin a user to one instance. Treat it as a
crutch for applications you cannot change: it unbalances the fleet, and when that instance
dies the user loses their session anyway.

<Callout type="gotcha" title="The step Kettle & Fox nearly skipped">
Their shop kept baskets in the web server's memory, which was invisible while there was only
one web server. Switch on Auto Scaling before fixing that and you get a *worse* Tuesday, not a
better one: shoppers get bounced between instances, baskets empty themselves halfway through
checkout, and every scale-in event throws away somebody's order. **Statelessness is not the
fourth step you do eventually — it is the permission slip for the other three.**
</Callout>

## Decoupling: stop things failing together

**Tight coupling** is when component A calls component B directly and waits. If B is slow, A is
slow. If B is down, A is down — and the failure travels outward to the user.

**Amazon SQS** puts a queue between them. The web tier writes a message and returns immediately;
workers read messages when they can. Now:

- A slow worker creates a backlog, not an outage.
- Workers can be scaled on **queue depth**, which is a far better signal than CPU.
- A worker that crashes mid-job does not lose it — the message becomes visible again after the
  **visibility timeout** and another worker picks it up.
- The web tier and the worker tier can be deployed, scaled and broken independently.

Its companions:

- **Amazon SNS** — publish/subscribe. One message, many subscribers. The classic pattern is
  **fan-out**: publish to an SNS topic with several SQS queues subscribed, so each downstream
  system gets its own copy.
- **Amazon EventBridge** — an event bus that routes by rules, including events from AWS services
  and third-party SaaS. The modern choice for event-driven architecture.

<Callout type="exam">
Watch for the words <strong>"decouple"</strong>, <strong>"the components should scale
independently"</strong> or <strong>"requests must not be lost during a spike"</strong>. Those
point at <strong>SQS</strong>. If one message must reach <em>several</em> different consumers,
that is <strong>SNS</strong>, usually fanning out to SQS queues.
</Callout>

---

Kettle & Fox run two small instances across two Availability Zones, a load balancer in front,
baskets in DynamoDB, and a group allowed to grow to twenty. It costs less per month than the
maintenance contract on the old server did.

They have been on television twice since. Neither time did anyone notice, which is the entire
point: **high availability is the discipline of making your best day and your worst day look
identical from the outside.**
