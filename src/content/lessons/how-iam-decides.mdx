## 02:14 — the billing alarm

A four-person analytics company. Two days earlier a developer had pushed a tidy little
refactor: the reporting service moved from a hard-coded path to a config file. The config file
had a comment above it that said `# TODO: move to secrets manager`, and underneath the comment,
in plain text, an AWS access key.

The repository was private. On Tuesday it was made public, because someone wanted to show a
recruiter their work.

**Nine minutes** after that push, GPU instances started launching in Regions the company had
never used. Not because anybody guessed a password — because bots continuously scrape public
commits for anything matching `AKIA…`, and a leaked AWS key is worth money the moment it is
found. By 02:14 the bill was past $8,000 and climbing in four Regions at once.

Here is the part that matters for the exam, and for your job:

> **AWS was not breached. AWS did exactly what it was told.** Every one of those
> `RunInstances` calls was evaluated against the same rules as every other request, and every
> one came back *Allow*.

The post-mortem question is not "how did they get in". It is **why did the answer come back
yes** — and that question has a fixed, four-step answer you can memorise today.

## Every action is a request

Clicking a button in the console, running a CLI command, an application calling an API — all of
it arrives at AWS as the same kind of thing: a **request** carrying *who* is asking, *what* they
want to do, *which* resource they want to do it to, and context such as source IP and whether
MFA was used.

**IAM** (Identity and Access Management) is the service that answers yes or no. It is free, it
is global rather than per-Region, and it runs the same sequence on every single request —
including the ones launching mining rigs at two in the morning.

### Now run the stolen key through those four steps

`RunInstances` in `ap-northeast-1`, using the key from the config file. Walk the gates:

1. **Explicit Deny?** There were no Deny statements anywhere in the account. Nobody had written
   one, because nobody had imagined needing one. → *pass*
2. **SCP guardrail?** The company had a single AWS account and no AWS Organization, so there
   was no ceiling to be outside of. → *pass*
3. **Any Allow?** The key belonged to an IAM user in the `Developers` group, and that group had
   `AdministratorAccess` attached, because in month one it was easier than working out what the
   reporting service actually needed. `"Action": "*"` on `"Resource": "*"`. → *pass*
4. **Verdict:** Allow. Four Regions. $8,000.

Every gate did its job. The gates were simply all wide open.

<Callout type="gotcha" title="The nine minutes are real">
AWS itself scans public repositories for exposed keys and will attach a quarantine policy
(`AWSCompromisedKeyQuarantineV2`) when it finds one — but that is a backstop measured in
minutes, and mining bots are faster. Treat any key that has ever touched a repository, a log, a
screenshot or a Slack message as **already public**: deactivate it, delete it, and check
CloudTrail for what it did in the meantime.
</Callout>

## Be the evaluator

Same company, rebuilt. Alice now deletes an old report through a role, with a Region guardrail
overhead and a bucket policy that insists on MFA. The command is real, the error messages are
the ones AWS actually returns.

Flip the switches and find every way to get told no — then read the last few words of each
`AccessDenied`. **That tail names the gate that stopped you**, and it is the single most useful
IAM debugging habit you can build.

<Callout type="exam" title="Read the tail of the error">
Those three endings are worth memorising, because they map exactly onto the evaluation order:
<br />· <code>…with an explicit deny in a resource-based policy</code> → a bucket, KMS key or
queue policy said Deny.
<br />· <code>…with an explicit deny in a service control policy</code> → you are outside the

<br />· <code>…because no identity-based policy allows the action</code> → nothing denied you,
nothing allowed you either. Implicit deny. Go and grant the permission.
</Callout>

## The four things IAM is made of

Four nouns, and the incident above involved three of them going wrong.

**Users** are people, or occasionally a legacy application. A user has a name, optionally a
console password, and optionally long-lived **access keys** for programmatic use. Users are
permanent identities, and their credentials sit around until somebody rotates them —
*which is exactly why one could still launch instances two days after it was pasted into a
config file.*

**Groups** are just a convenient bundle of users. Attach the policy to `Developers` once
instead of to fourteen people individually. Groups cannot be nested, and a group is **not an
identity** — you cannot make a group the principal of anything. *The reporting service was in
`Developers` because that was the group that already existed. Convenience is how blast radius
grows.*

**Roles** are identities that **nobody owns and anybody approved can temporarily become**.
A role has permissions but no password and no permanent keys. When something assumes a role it
receives temporary credentials that expire in an hour or so. Roles are how an EC2 instance
talks to S3, how a Lambda function reads DynamoDB, how one AWS account grants access to
another, and how a user logging in through your company's identity provider gets permissions.

**Policies** are JSON documents that say what is permitted. Attached to a user, group or role
they are *identity-based*; attached to an S3 bucket, a KMS key or an SQS queue they are
*resource-based*.

<Callout type="analogy">
A user is an employee with a permanent staff badge. A role is the hi-vis jacket hanging by the
loading-bay door: nobody owns it, it grants exactly the access needed on the loading bay, and
you hang it back up when you leave. If someone steals a badge they have it forever. If they
find the jacket after hours, it has already stopped working.
</Callout>

## What a policy actually says

Here is the policy that cost $8,000. It is the real `AdministratorAccess`, and it is four lines
long:

```json
{
  "Version": "2012-10-17",
  "Statement": [{ "Effect": "Allow", "Action": "*", "Resource": "*" }]
}
```

And here is what the reporting service was actually doing all along — read one file per night
from one prefix:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ReadNightlyReportsOnly",
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:PutObject"],
      "Resource": "arn:aws:s3:::company-reports/2026/*",
      "Condition": {
        "Bool": { "aws:MultiFactorAuthPresent": "true" }
      }
    }
  ]
}
```

Same document format, same evaluation, wildly different worst case. Every statement answers
five questions, and being able to read one is worth more than memorising service names:

- **Effect** — `Allow` or `Deny`.
- **Action** — which API calls, in `service:Operation` form. Wildcards are permitted, and
  `"Action": "*"` is how you accidentally grant everything, including `iam:CreateUser` and
  `ec2:RunInstances` in Regions you have never opened.
- **Resource** — which ARNs it applies to. Note the `/2026/*`: permissions can be narrowed to a
  prefix inside a bucket, not just to the bucket.
- **Condition** — optional extra tests. This one refuses unless the caller authenticated with
  MFA. Conditions are also how you restrict by source IP, by time of day, by tag, and by Region.
- **Principal** — *who* it applies to. It appears only in **resource-based** policies; in an
  identity-based policy the principal is whatever the policy is attached to.

<Callout type="gotcha" title="Bool vs BoolIfExists — the MFA trap">
Writing a **Deny** with `"Bool": {"aws:MultiFactorAuthPresent": "false"}` looks right and
quietly does nothing in the cases you care about. For calls that never had an MFA context — an
EC2 instance role, a Lambda — the key is **absent** rather than `false`, the condition does not
match, and the Deny never fires. Use `BoolIfExists` for that check, which treats "missing" as
"not MFA".
</Callout>

<Callout type="exam">
Watch for questions where a user "has an Allow from their group but still cannot access the
bucket". Look for an explicit <strong>Deny</strong> somewhere — in another attached policy, a
bucket policy, an SCP or a permissions boundary. The explicit Deny always wins, and that is
almost always what the question is testing.
</Callout>

## Roles, and the rule about access keys

The whole story turns on one line in one config file, so this rule is worth stating bluntly:

> **Never put access keys on an EC2 instance. Attach an IAM role.**

Access keys hard-coded into an application, baked into an AMI or left in a configuration file
are permanent credentials that leak — into Git repositories, into logs, into screenshots, into
the Slack message where someone asks why the job is failing. An IAM role attached to the
instance delivers **temporary credentials** through the instance metadata service, rotates them
automatically, and there is nothing on disk to steal. The `# TODO: move to secrets manager`
comment is the tell: if you are writing that comment, you already know, and a role is less work
than the TODO.

The same reasoning applies everywhere:

- **EC2 needs to read S3** → an instance profile with an IAM role.
- **Lambda needs to write to DynamoDB** → an execution role.
- **An application in another AWS account needs your bucket** → cross-account role assumption.
- **Your staff need console access** → **IAM Identity Center** (formerly AWS SSO) federating to
  your existing directory, so people keep one corporate login and you create no IAM users at all.
- **A mobile app needs to upload photos** → temporary credentials from **Amazon Cognito**, never
  embedded keys.

<Callout type="gotcha">
The <strong>root user</strong> — the email address the account was created with — can do
absolutely anything, including closing the account and undoing security controls. Set up MFA on
it, delete any access keys it has, and then do not use it. AWS lists only a handful of tasks
that genuinely require it (changing the account's support plan, closing the account, some
billing settings). Everything else should be an IAM identity.
</Callout>

## Least privilege, and the tools that get you there

**Least privilege** means granting exactly the permissions needed and no more. It is easy to
say and tedious to do, so AWS provides help.

<Callout type="note" title="Start with a managed policy, then tighten">
Everything above may have left you with the impression that you must write a perfect,
minimal policy before you are allowed to build anything. You must not, and believing so is
exactly what drives people to attach <code>AdministratorAccess</code> and move on — the
outcome least privilege exists to prevent.

The workable order is: reach for an **AWS managed policy** that roughly fits — there are
hundreds, and <code>AmazonS3ReadOnlyAccess</code> is a far better starting point than
<code>AdministratorAccess</code> — get the thing working, and <em>then</em> narrow it using the
tools below once you can see what it actually called. Access Analyzer will generate a
tight policy from real CloudTrail activity, which is easier and more accurate than guessing.

Least privilege is a direction of travel, not an entry requirement. What matters is that
"temporarily" wide permissions have a date attached and somebody actually comes back.
</Callout>

The tools that get you there:

- **IAM Access Analyzer** finds resources shared outside your account, and can generate a
  tightly-scoped policy from what an identity has *actually* used in CloudTrail.
- **Last accessed information** shows which services a user or role has not touched in months —
  a straightforward list of permissions to remove.
- **Permissions boundaries** cap the maximum permissions an identity can have, which lets you
  safely let a team create their own roles without letting them create an administrator.
- **IAM Policy Simulator** answers "would this request be allowed?" before you find out the
  hard way. From the CLI:

  ```bash
  aws iam simulate-principal-policy \
    --policy-source-arn arn:aws:iam::123456789012:role/reporting-service \
    --action-names s3:GetObject \
    --resource-arns arn:aws:s3:::company-reports/2026/q3.pdf
  ```

## The rebuild, in three artifacts

This is what the company shipped in the week after, and it is a template worth stealing. Notice
that each piece plugs into a different gate of the evaluation you just learned.

**Gate 2 — a Region guardrail.** An SCP on the organisation, denying everything outside the two
Regions they operate in. This is the one that would have ended the incident at minute one:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyUnapprovedRegions",
      "Effect": "Deny",
      "NotAction": ["iam:*", "sts:*", "cloudfront:*", "route53:*", "support:*"],
      "Resource": "*",
      "Condition": {
        "StringNotEquals": {
          "aws:RequestedRegion": ["eu-west-1", "eu-west-2"]
        }
      }
    }
  ]
}
```

The `NotAction` list matters: IAM, STS, CloudFront and Route 53 are **global** services whose
calls land in `us-east-1`, so a naive Region lock locks you out of your own account.

**Gate 3 — a role instead of a key.** The reporting service now assumes a role. The *trust*
policy says who may become it; the permissions policy says what they can then do:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": { "Service": "ec2.amazonaws.com" },
      "Action": "sts:AssumeRole"
    }
  ]
}
```

Credentials now arrive through the instance metadata service, expire in an hour, and are never
written to disk. There is nothing left in the repository to leak.

**Gate 1 — an explicit Deny on the data itself.** A bucket policy that refuses deletes from
anyone who did not authenticate with MFA, no matter what their identity policy says:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "NoDeletesWithoutMFA",
      "Effect": "Deny",
      "Principal": "*",
      "Action": "s3:DeleteObject",
      "Resource": "arn:aws:s3:::company-reports/*",
      "Condition": {
        "BoolIfExists": { "aws:MultiFactorAuthPresent": "false" }
      }
    }
  ]
}
```

That is the exact switch labelled *"Bucket policy denies without MFA"* in the simulator above —
scroll back and turn it on, and watch it beat an Allow that is still sitting right there.

<Callout type="note" title="Three commands for the next time you are stuck">
· <code>aws sts get-caller-identity</code> — who am I *actually* right now? Answers more
"permission" problems than you would expect, because the answer is often "a different principal
than you assumed".
<br />· <code>aws iam simulate-principal-policy …</code> — would this be allowed? Test before
you deploy.
<br />· CloudTrail, filtered to <code>errorCode = AccessDenied</code> — every refusal is logged
with the principal, the action and the resource. This is the audit trail that answered "what did
the leaked key do" in the story above.
</Callout>

The company in this lesson is still trading. Nothing about their recovery was clever: a role
instead of a key, a Region guardrail, an explicit Deny on the data that matters, and MFA on the
humans. Four small artifacts, each one plugging into a gate you can now name in order.

That is the whole trick. IAM is not a wall of jargon — it is one sequence, run on every request
ever made, and you have just watched it run.
