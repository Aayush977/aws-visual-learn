## The question after the question

A contractor left a fintech in March, under a cloud, having had broad access for eighteen
months. In April the general counsel asked the engineering lead two questions.

The first was easy. *Is the customer data encrypted?* Yes. All of it, at rest and in transit,
every bucket and every database, ticked and evidenced.

The second question took four weeks. *Then prove he can no longer read it.*

Nobody could. Not because anything was wrong — the encryption was real, the ciphertext was
genuinely unreadable without a key — but because the data was encrypted under **AWS managed
keys**, which are handed out to whoever the IAM policies say can use them, and those policies
were spread across a dozen roles that eighteen months of urgent tickets had quietly widened.

"Is it encrypted?" and "who can decrypt it?" felt like the same question. They are not remotely
the same question, and only the second one has ever protected anybody.

## Encryption is the easy half

Encrypting data on AWS is close to free and usually a checkbox. That is precisely why the exam
does not ask *whether* to encrypt — it asks **who holds the key**, and what happens when
somebody who should not have it asks for your data.

There are only two states data can be in, and each has its own answer.

## In transit — TLS, and the certificate service

Anything crossing a network should be encrypted in transit, which in practice means **TLS**
(the protocol people still call SSL). You need a certificate to do it, and **AWS Certificate
Manager (ACM)** issues them:

- **Free** for use with AWS services — load balancers, CloudFront, API Gateway.
- **Renewed automatically**, which quietly eliminates one of the most common causes of
  self-inflicted outages.
- Certificates are **Regional**, and a certificate used by CloudFront must live in
  **us-east-1** regardless of where the rest of your stack is.

<Callout type="gotcha">
ACM certificates cannot be exported for use on your own servers outside AWS. If a question
mentions installing a certificate on an on-premises appliance, ACM is wrong — you need a
certificate from elsewhere, or ACM Private CA.
</Callout>

## At rest — AWS KMS

**AWS Key Management Service** creates and controls the keys that encrypt your data. The
important mechanic is that the **KMS key itself never leaves KMS**. When S3 encrypts an object
it asks KMS for a *data key*, uses it in memory, and discards it — a pattern called **envelope
encryption**.

The consequence is the thing worth remembering: **access to encrypted data is an IAM question,
not a cryptography question.** Remove a principal from the key policy and their access ends
immediately, without touching a single byte of stored data.

This is exactly what the fintech could not do. A key policy is a short document naming who may
use a key; when you use AWS managed keys you do not get to write one, so "who can decrypt this?"
has no single place to look — it is the union of a dozen IAM policies, and answering it means
auditing all of them. Move to a customer managed key naming three roles, and the same question
takes **one screen and about nine seconds**.


Three kinds of key, and the exam distinguishes them:

| Key type | Who creates it | Who can rotate it | Cost |
| --- | --- | --- | --- |
| **AWS owned** | AWS, shared across accounts | AWS | Free, invisible to you |
| **AWS managed** (`aws/s3`) | AWS, one per service per account | AWS, annually | Free |
| **Customer managed** | You | You — automatic yearly rotation, or on demand | Monthly charge per key, plus API calls |

You want a **customer managed key** whenever a question mentions *controlling* the key: custom
rotation schedules, a key policy naming specific principals, cross-account grants, or the
ability to disable a key and lock everyone out at once.

<Callout type="exam">
"Encryption keys must be rotated on a schedule the company controls", "the security team must
be able to revoke access to encrypted data", or "keys must be shared with another AWS account"
→ <strong>customer managed KMS key</strong>. If the requirement is only "the data must be
encrypted at rest", an AWS managed key is enough and cheaper.
</Callout>

## CloudHSM — when you must be the only one with the key

**AWS CloudHSM** gives you a dedicated, single-tenant hardware security module. It is
FIPS 140-3 Level 3 validated, and **AWS has no access to your keys at all** — which is exactly
the point, and also the risk: lose them and nobody, including AWS, can recover your data.

Choose it only when a regulator or contract requires single-tenant hardware or the ability to
prove AWS cannot access the keys. KMS is multi-tenant and right for nearly everyone else.

## Secrets Manager, and the thing it is confused with

A **secret** is not a key — it is a database password, a third-party API token, an OAuth
credential. **AWS Secrets Manager** stores them encrypted with KMS, hands them to applications
over an API, and — the feature that justifies its price — **rotates them automatically**,
including natively rotating RDS credentials.

It is routinely confused with **Systems Manager Parameter Store**, which also stores
configuration values and can encrypt them:

| | **Secrets Manager** | **Parameter Store** |
| --- | --- | --- |
| Built for | Secrets | Configuration, and secrets if you like |
| Automatic rotation | **Yes**, built in | No, you build it yourself |
| Cross-account sharing | Yes | No |
| Cost | Per secret per month | Standard tier is **free** |

<Callout type="cost">
If a question stresses <strong>automatic rotation</strong> of a database credential, the answer
is <strong>Secrets Manager</strong>. If it stresses storing configuration or secrets
<strong>at no additional cost</strong>, it is <strong>Parameter Store</strong>. That single
word — rotation or cost — decides it almost every time.
</Callout>

## Encryption you get without asking

Worth knowing because questions sometimes offer "enable encryption" as a distractor when it is
already on:

- **S3** encrypts every new object by default with SSE-S3. You can upgrade to SSE-KMS for key
  control, or SSE-C if you insist on supplying keys yourself.
- **EBS** volumes can be encrypted by default account-wide, and snapshots of an encrypted
  volume are encrypted too.
- **RDS** encryption must be chosen **when the instance is created** — you cannot encrypt an
  existing unencrypted RDS instance in place. You restore a snapshot into a new encrypted one.
- **DynamoDB** encrypts all tables at rest, always, with no option to turn it off.

<Callout type="gotcha">
The RDS detail is a favourite. "An existing unencrypted RDS database must be encrypted" is not
a settings change — you take a snapshot, copy the snapshot with encryption enabled, and restore
it into a new instance. Any answer that just enables encryption on the running database is wrong.
</Callout>

---

The fintech's four-week answer is now a one-line one: three roles are named in one key policy,
and every `Decrypt` call against that key is in CloudTrail with a name and a timestamp.

Nothing about their cryptography changed. The same algorithm, the same ciphertext, the same
checkbox ticked in the same console. What changed is that somebody can now **answer the second
question** — and the second question is the only one an auditor, a regulator or an attacker has
ever cared about.

Encryption is a checkbox. Key management is a decision. Only one of them is on the exam, and
only one of them would have helped in April.
