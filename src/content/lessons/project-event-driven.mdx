## The problem

When a radiographer at Aldgate Health uploads a scan, four separate things need to happen: a
thumbnail for the browser list, an entry in the searchable index, a check that no patient
identifiers are sitting in the file, and a notification to the consultant who requested it.

The obvious implementation is one program that does all four in order. It is also the wrong one,
and it fails in a specific, familiar way: the notification service goes down at 2am, so the
upload fails, so the *radiographer* cannot upload a scan — because the mail server is unwell.
Four unrelated things have been tied together into one thing that fails as a unit.

Worse, adding a fifth consumer next year means editing, retesting and redeploying the code that
handles uploads. The upload path becomes the most dangerous file in the codebase, because
everything ends up in it.

## Why SNS *and* SQS, rather than one of them

This is the pattern's whole trick, and it is worth being precise about why both are there.

**Why not have S3 call the four Lambdas directly?** S3 can trigger Lambda, and for *one*
consumer that is the right, simplest answer. It stops being right at the point where a second
consumer appears: you would be reconfiguring the bucket every time the business grows a new
interest in uploads, and the bucket would slowly accumulate knowledge of every system in the
company.

**EventBridge instead of SNS?** A fair question, and increasingly the modern default. Reach for
**EventBridge** when routing should depend on the *content* of the event — send MRI scans one
way and X-rays another — or when events come from other AWS services or third-party SaaS. Reach
for **SNS** when everybody simply gets everything. Aldgate's four consumers all want every
upload, so SNS is the simpler correct answer.

<Callout type="exam" title="The giveaway sentence">
<strong>"Each system must receive a copy of every message"</strong> plus <strong>"no message may
be lost if a system is unavailable"</strong> is the exam describing SNS fanning out to SQS. If
only the first half is present, plain SNS is enough. If neither, a single SQS queue.
</Callout>

## Roughly what it costs

This is the cheapest architecture in this section by a distance, because everything is priced
per message and there is nothing to keep running.

| Line | Rough monthly cost |
| --- | --- |
| S3 event notifications | free |
| SNS — first million publishes | free tier, then cents per million |
| SQS — first million requests | free tier, then cents per million |
| Lambda — first million invocations | free, then about $0.20 per million |
| **Typical total at modest volume** | **pennies** |

The property worth taking from this one is not cost or even resilience. It is that **nothing in
this diagram knows about anything else.**

S3 does not know four systems care about uploads. The thumbnail worker has never heard of the
notifier. When somebody asks next year for uploads to also trigger an audit log, that is a new
queue and a new function, and not one existing component is touched, retested or redeployed.

That property has a name the exam uses constantly — **decoupling** — and this is what it buys.
