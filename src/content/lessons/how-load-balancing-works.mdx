## The second server that broke everything

Brightwell's claims portal ran on one server, and everyone agreed that was a risk. So they did
the obvious, responsible thing: they added a second one and put a load balancer in front.

The support queue filled up within an hour.

Customers were being logged out in the middle of a claim. Not all of them, and not
consistently — a form would submit fine, then the next page would bounce them to the login
screen, then the page after that would work again. One customer got three quarters of the way
through uploading photographs of a flooded kitchen and lost the lot.

The engineers checked both servers. Both were up. Both were serving pages. Both had the
correct code. The load balancer reported two healthy targets and was cheerfully splitting
traffic between them, which is precisely what they had asked it to do and exactly what was
destroying every session.

**Nothing had failed. The second server was working perfectly — and that was the problem.**

## One address in front of many machines

A load balancer is a single, stable address that stands in front of a changing set of machines
and hands each arriving request to one of them.

Everything awkward about it follows from that one sentence. If a request can go to *any*
machine, then **no machine is allowed to be special** — and a server holding the only copy of
your session is very special indeed. Brightwell's sessions were stored on local disk. Half the
requests landed on a server that had never heard of that customer, and the only honest thing
for it to do was ask them to log in again.

That is the shape of nearly every load balancer problem: something that used to be safe to keep
on one machine is no longer safe to keep on one machine.

## Health checks, and what "healthy" should mean

The health check is the most under-thought setting in AWS, and it decides whether your outage
lasts thirty seconds or all afternoon.

A target group probes each target on a schedule. Four numbers control it:

- **Interval** — how often to probe.
- **Timeout** — how long to wait for an answer before calling it a failure.
- **Unhealthy threshold** — how many consecutive failures before the target is pulled out.
- **Healthy threshold** — how many consecutive successes before it is allowed back in.

Plus a **path** and a **success matcher** (which HTTP codes count as a pass).

### The trap: checking the wrong thing

Point the health check at `/` and you are usually asking the *web server* whether it is alive.
It will happily say yes while the application behind it cannot reach the database, cannot read
its configuration, and is returning an error page to every real customer — with a 200 status,
because the error page rendered successfully.

The load balancer has no way to know. It asked a question and got the answer it was told to
accept.

**Point the health check at an endpoint that exercises the thing that actually matters.** A
`/healthz` that checks it can reach the database and returns 503 when it cannot is worth more
than any monitoring you can buy, because the load balancer acts on it automatically and
instantly.

<Callout type="gotcha">
The opposite mistake is just as common: a health check that is <em>too</em> thorough. If
<code>/healthz</code> queries the database and the database has a slow minute, <strong>every
target fails at once</strong> and the load balancer takes the entire fleet out of service over
a problem that would have resolved itself. Check what this instance needs to serve a request —
not the health of every downstream system it has ever spoken to.
</Callout>

### Draining, so nobody is cut off mid-request

When a target is removed — a scale-in, a deploy, a manual deregistration — it stops receiving
*new* requests but is given time to finish the ones it already has. This is the
**deregistration delay**, sometimes called connection draining, and it defaults to five
minutes.

Too short and you cut people off mid-upload. Too long and every deploy crawls. Set it to
slightly longer than your slowest normal request, not your slowest imaginable one.

### Cross-zone load balancing

Targets live in more than one Availability Zone, and there is a question about whether a
balancer node in one zone may send traffic to targets in another.

- **Application Load Balancer:** cross-zone is **always on**. Traffic is spread evenly across
  all healthy targets regardless of zone.
- **Network Load Balancer:** it is **off by default**. Each zone's node sends only to targets
  in its own zone, which means uneven zones get uneven load — four targets in one AZ and one in
  another means that single target receives the same share as the other four combined.

<Callout type="exam">
"Traffic is not evenly distributed across instances" with an NLB in the question is nearly
always <strong>cross-zone load balancing being disabled</strong>, or unequal numbers of targets
per Availability Zone. With an ALB, look elsewhere — it cannot be the cause, because it is
always enabled there.
</Callout>

## Sessions: the real fix and the plaster

Back to Brightwell. There are two ways out of the logged-out problem, and the exam cares that
you know which is which.

**The plaster is sticky sessions.** The load balancer issues a cookie that pins a customer to
the same target for a period. The logouts stop immediately, which is why this is what almost
everyone reaches for first.

It also brings back every problem the load balancer existed to solve. That target is now
special again: when it fails, everyone pinned to it loses their session anyway. Scaling out
does not help existing customers, because they are already attached elsewhere. And load goes
lopsided, because customers do not distribute themselves evenly.

**The real fix is to move the state off the instance**, so no target is ever special:

- Sessions into **ElastiCache for Redis** or **DynamoDB**, where every instance can reach them.
- Uploaded files into **S3**, not local disk.
- Anything written during a request into a **database**, not a temporary directory.

Now an instance can be destroyed mid-afternoon and nobody notices. That property — a machine
being disposable — is what makes auto scaling, rolling deploys and self-healing possible at
all. Sticky sessions buy you an afternoon; statelessness buys you the architecture.

<Callout type="exam">
When a question describes users losing sessions behind a load balancer and asks for the
<strong>most scalable</strong> or <strong>most resilient</strong> answer, it wants the session
store — ElastiCache or DynamoDB. Sticky sessions will be offered, and it is the right answer
only when the question explicitly rules out changing the application.
</Callout>

## Build it yourself

This lesson is mostly about things you cannot see from outside — a health check probe, a target
being pulled from rotation, a session that exists on one machine and not another. The way to
see them is to build two load balancers and then deliberately break one target.

### Why this one, when it is not a load balancer workshop

Because it builds **two** load balancers doing genuinely different jobs, and the contrast is
what makes the concept stick:

- The **external** ALB is internet-facing, in public subnets, and is the only public surface.
- The **internal** ALB is not reachable from the internet at all. The web tier calls it by its
  DNS name to reach the application tier.

Most tutorials show you one load balancer in front of one thing, which teaches the shape but
not the idea. Two makes it obvious that a load balancer is a *seam between tiers*, not a front
door.

### Step by step, in the order the concepts appear above

1. **Network first** — VPC, public and private subnets across two Availability Zones. Nothing
   in this lesson works without two zones, because there is nothing to spread across.
2. **Launch the app tier instances** into private subnets and confirm they are unreachable from
   the internet. This is the property the load balancer exists to preserve.
3. **Create the internal target group and health check.** This is the moment that matters —
   you choose the path and the thresholds by hand. Point it at the application's own health
   endpoint, not at `/`.
4. **Create the internal ALB** and register the target group. Watch the targets go from
   `initial` to `healthy` in the console. That transition is the health check passing for the
   first time.
5. **Configure Nginx on the web tier** to proxy `/api` to the internal load balancer's DNS
   name. Note that it uses a *name*, not an address — the whole point of the seam.
6. **Repeat for the web tier**: target group, health check, internet-facing ALB.
7. **Auto Scaling groups at both tiers**, attached to the target groups. Registration and
   deregistration now happen without you.

### Break it on purpose

The workshop ends with a working site. That is where the actual lesson starts.

1. **Stop the application process on one instance** but leave the instance running. The health
   check fails, the target is marked unhealthy, and the site keeps working — you have just
   watched automatic failover happen with no alarm and no human.
2. **Now point the health check at `/` instead** and repeat. The target stays `healthy` while
   serving nothing, and half your requests break. This is the single most valuable five minutes
   in the whole lab: it is the difference between a health check and a *useful* health check.
3. **Set the unhealthy threshold to 10 with a 30-second interval** and kill a target. Count how
   long the broken instance keeps receiving traffic. Then set it to 2 and do it again.
4. **Store something in memory on one instance** — even a counter in the app — and refresh
   repeatedly. Watch the number jump around as you land on different targets. That is
   Brightwell's bug, reproduced in thirty seconds.
5. **Terminate an instance mid-request** with the deregistration delay set to 0, then to 60.
   The difference is whether a user sees an error or does not notice.

<Callout type="cost" title="This one runs real instances">
Unlike most labs on this site, this leaves EC2 instances, two load balancers and an Aurora

<strong>Delete it the same day.</strong> Work backwards: Auto Scaling groups first (or they

Brightwell's second server was never broken. It was doing exactly what a second server does,
and it exposed an assumption nobody knew they had made: that the machine which started a
customer's session would be the machine that finished it.

That assumption was invisible for as long as there was only one machine to make it on. This is
what people mean when they say the cloud requires a different way of thinking — not that the
servers are different, but that **you are no longer allowed to know which one you are talking
to**, and anything you were quietly keeping on it has to go somewhere every server can reach.

Adding the second server did not cause the bug. It revealed one that had been there since the
first day.
