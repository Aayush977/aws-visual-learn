## The problem

Meridian — the four-person analytics company from the IAM lesson — sell a dashboard. Their
customers' browsers need to ask questions like *"give me last month's figures for account
4471"* and get an answer back.

The load is not large and it is extremely uneven. Weekday mornings are busy. Nights and weekends
are dead. Once a quarter, on results day, it is twenty times normal for about an hour.

With four engineers, the constraint is not really traffic. It is that **nobody has time to look
after servers.** Anything requiring a patching schedule or a capacity review will simply not get
done, and will quietly become a security problem.

## Why each piece, and not the obvious alternative

**API Gateway** is doing more than routing, and this is the bit that is easy to undervalue.
Authentication, throttling, request validation, CORS and API keys are all *there* — features
every API needs, that every team otherwise writes badly. Without it, that work lands inside your
Lambda function, where you own it forever.

**DynamoDB** rather than a relational database, for one specific reason: the query is always
*"give me this account's figures"* — a lookup by key. A key-value store answers that in
single-digit milliseconds whether the table holds a thousand rows or a billion, and it needs no
instance, no patching and no capacity planning. Ask a *different* shape of question — joins,
ad-hoc reporting, "all customers who did X and Y" — and this becomes the wrong choice fast.

<Callout type="exam" title="The phrase that names this architecture">
When a scenario says <strong>"without managing any servers"</strong> or <strong>"minimal
operational overhead"</strong> alongside <strong>"variable"</strong> or
<strong>"unpredictable"</strong> traffic, it is describing this stack. The answer is almost
always <strong>API Gateway + Lambda + DynamoDB</strong>, and the distractors are usually the
same architecture on EC2.
</Callout>

## Where this stops being the right answer

Every architecture has an edge, and pretending otherwise is how people get burned.

- **Cold starts.** A function that has not run recently takes extra time to start — usually tens
  to hundreds of milliseconds. Irrelevant for a dashboard, potentially unacceptable for a
  latency-critical trading path.
- **The 15-minute ceiling.** Lambda stops at 15 minutes. Video encoding, large batch jobs and
  long migrations do not fit and belong on Fargate or EC2.
- **Steady, heavy load.** Per-millisecond billing is superb when you are idle most of the time.
  A function running flat out 24 hours a day can cost more than an equivalent instance — and at
  that point the idleness argument, which is the whole case for Lambda, no longer applies.
- **The wrong query shape.** DynamoDB punishes access patterns you did not design for. If you
  cannot say in advance how the data will be queried, a relational database is more forgiving.

## Roughly what it costs

Rough figures for a small API, and hedge them with the Pricing Calculator before trusting them.

| Line | Rough monthly cost |
| --- | --- |
| Lambda — first 1M requests/month | free, always, then about $0.20 per million |
| API Gateway (HTTP API) — per million requests | roughly $1 |
| DynamoDB on-demand — modest read/write volume | a few pounds |
| CloudWatch Logs — modest retention | pennies to a pound |
| **Typical total for a small API** | **often under £5** |

Notice how much of this architecture is *absence*. No instances, no Auto Scaling group, no load
balancer, no patch schedule, no capacity decision, and nothing running at three in the morning.

For a team of four that is not a cost saving so much as a **staffing** one. The work that
usually consumes a small team's attention — keeping the lights on — has largely been bought
rather than done, and the exam's phrase for buying it is *reducing operational overhead*.
