## The problem

Aldgate Health have a Lambda function that reads a database password from **Secrets Manager**
and writes a report to **S3**. Both perfectly ordinary things to do.

The security team's requirement is equally ordinary: the function handles patient data, so it
must sit in a **private subnet** with no route to the internet.

And then it stops working, with a timeout rather than an error — which is the most confusing
possible failure, because a timeout looks like a bug in your code.

Here is what is actually happening, and it catches almost everybody once. AWS service APIs live
on **public** endpoints. `secretsmanager.eu-west-1.amazonaws.com` is a public hostname. So the
moment you put a function in a private subnet, you have cut it off from the very services it
needs — because "no internet access" turns out to include AWS itself.

There are three ways out of this, and choosing between them is worth real money.

**Why is one free and the other not?** Because they are genuinely different mechanisms. A
gateway endpoint is a *routing* change — AWS adds a prefix list to your route table and no
resource is created inside your VPC. An interface endpoint creates a real **elastic network
interface**, consuming an IP address in your subnet, in each Availability Zone you choose. You
are paying for a thing that exists.

That difference explains the rest of the table. Only the interface endpoint can have a
**security group**, because only it has a network interface for one to attach to. And only it
can be reached from your own data centre, because a route table entry means nothing to a server
that is not in the VPC.

<Callout type="cost" title="The gateway endpoint is free money">
If a VPC has private instances talking to S3 through a NAT gateway, you are paying twice — once
for the NAT hours and again for every gigabyte it processes — to reach a service that would
answer for free over a gateway endpoint.

This is one of the few genuinely free wins on AWS, and it is why <strong>"reduce NAT gateway
costs"</strong> in an exam question is almost always answered with <strong>"create a gateway
VPC endpoint for S3"</strong>.
</Callout>

## Private DNS, and why the timeout was so confusing

Worth dwelling on, because it explains the failure this lesson opened with.

When you enable **private DNS** on an interface endpoint, AWS creates a private hosted zone so
that inside your VPC, `secretsmanager.eu-west-1.amazonaws.com` resolves to the endpoint's
private address instead of the public one. Everywhere else in the world it still resolves
normally.

The consequence is the nice part: **no application code changes.** The SDK, the CLI and your
function all keep using the ordinary public hostname.

The consequence when it is *not* set up is the nasty part. The name still resolves — to a public
address — and your function dutifully tries to reach it, and there is no route, so it sits there
until it times out. **A missing endpoint does not look like a permissions error. It looks like
your code hanging**, which is why people lose an afternoon to it.

<Callout type="gotcha" title="Three things that produce the same timeout">
When something in a private subnet cannot reach an AWS service, check these in order — they all
fail identically:
<br />1. <strong>Is there an endpoint at all?</strong> No endpoint and no NAT means no path.
<br />2. <strong>Is private DNS enabled</strong> on the interface endpoint? Without it the name
still points at the public address.
<br />3. <strong>Does the endpoint's security group allow HTTPS on port 443 inbound</strong> from
your function's security group? An interface endpoint is a network interface, and it is
firewalled like one.
</Callout>

## The full picture in the lab

The repository below builds exactly this, in four steps that stack: an interface endpoint for
Secrets Manager, a customer-managed KMS key, a secret encrypted with that key, and finally a
Lambda in private subnets that fetches it.

The Lambda is the part worth reading. Before calling Secrets Manager at all it resolves the
hostname and reports the IP it got back, then tests whether port 443 will open. That is a
genuinely good habit to steal: **when a private path fails, prove the DNS answer and the
connectivity separately**, because the timeout alone tells you nothing about which of the two
is broken.

It also ties this project to two other lessons. The **customer-managed KMS key** is the
*Encryption and Key Management* lesson made concrete — the key policy names exactly who may
decrypt. And putting the secret in Secrets Manager rather than an environment variable is the
rule from *How IAM Decides*: applications get roles and short-lived secrets, never credentials
sitting in a file.

The reason this project is worth the effort is that it is the first one where **the security
requirement and the cost saving point the same way.**

Usually they fight: the safer design costs more, and somebody has to argue for it. Here, taking
your S3 traffic off the public internet also takes it off the NAT gateway, and the bill goes
down while the blast radius shrinks.

Those alignments are rare enough that it is worth recognising one when you see it — and this is
the example the exam reaches for most often.
