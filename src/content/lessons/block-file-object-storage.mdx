Beginners usually meet AWS storage as a list of acronyms and try to memorise which is
"faster" or "cheaper". That is the wrong axis, and it produces wrong answers.

The real question is **how many machines need to reach this data at the same time, and do
they need it to look like a filesystem?** Answer that and the service picks itself.

## Block storage — Amazon EBS

An **EBS volume** is a virtual disk. The instance sees `/dev/xvdf`, you put a filesystem on
it, and from then on it is indistinguishable from a physical drive. This is what you want
whenever software expects a disk: a database's data directory, an operating system's boot
volume, anything doing lots of small random reads and writes.

The properties that get tested:

- **It lives in one Availability Zone.** If that AZ fails, so does the volume.
- **It attaches to one instance** at a time. (There is a Multi-Attach mode for `io1`/`io2`
  volumes and a handful of cluster-aware filesystems, but treat one-to-one as the rule and
  Multi-Attach as the footnote.)
- **It persists independently of the instance.** Terminate the instance and the volume can
  survive — though the root volume is set to delete on termination by default, which has
  surprised a great many people.
- **Snapshots go to S3** and are incremental. A snapshot can be restored into a *different*
  Availability Zone, which is how you move a volume across zones.

Volume types worth recognising:

| Type | Shape of workload | Note |
| --- | --- | --- |
| **gp3** | General purpose SSD | The sensible default. Throughput and IOPS are configured independently of size |
| **io2 Block Express** | Highest, most consistent IOPS | Large transactional databases. Expensive |
| **st1** | Throughput-optimised HDD | Big sequential reads — log processing, data warehouses. Cannot be a boot volume |
| **sc1** | Cold HDD | Cheapest, rarely touched. Cannot be a boot volume |

<Callout type="gotcha">
"Increase the IOPS" and "increase the size" used to be the same action. With **gp3** they are
not — you buy IOPS and throughput as separate dials. A question describing a volume that is
big enough but too slow is pointing at gp3 (or io2), not at a bigger disk.
</Callout>

## File storage — Amazon EFS (and FSx)

**EFS** is a filesystem on the network. Many instances mount it at the same path and every one
of them sees the same files, with ordinary POSIX permissions and file locking. It spreads
across Availability Zones by default, grows to petabytes without being resized, and you pay
for what you actually store.

This is the answer whenever a **fleet** of machines needs shared files: a content management
system where any web server might serve any upload, a shared home directory, a build farm
reading the same dependency cache.

The cost trap is that EFS is several times the price per gigabyte of EBS, and roughly ten
times that of S3 Standard. It is bought for the sharing, not for the storage.

Its siblings exist for cases where "a filesystem" means something more specific:

- **Amazon FSx for Windows File Server** — a genuine SMB share with Active Directory
  integration. The answer whenever a question mentions **Windows file shares**.
- **Amazon FSx for Lustre** — extremely high-throughput parallel filesystem for HPC and
  machine-learning training, able to present an S3 bucket as a filesystem.
- **Amazon FSx for NetApp ONTAP / OpenZFS** — for teams migrating an existing NetApp or ZFS
  estate and wanting the same features.

<Callout type="exam">
EFS is <strong>Linux/NFS</strong>. FSx for Windows File Server is <strong>Windows/SMB</strong>.
If the scenario says "Windows-based application requiring an SMB file share", EFS is wrong no
matter how well it fits everything else in the sentence.
</Callout>

## Object storage — Amazon S3

S3 stores **objects** — a blob of bytes, a key that names it, and metadata — inside a
**bucket**. You do not mount it. You call an API over HTTPS, and so can anything else with
permission, from an EC2 instance to a mobile app to a browser.

Giving up the filesystem buys a great deal:

- **Effectively unlimited capacity.** No volume to resize, ever. Individual objects up to 5 TB.
- **Eleven nines of durability** (99.999999999%), because every object is replicated across at
  least three Availability Zones automatically.
- **Reachable from anywhere**, with fine-grained permissions per object.
- **Cheap** — a small fraction of EBS or EFS per gigabyte, with colder tiers cheaper still.
- **It can serve a website directly**, and it is where CloudFront, Athena, and most analytics
  tooling expect your data to be.

What you gave up matters too. You cannot modify part of an object — every write replaces the
whole thing. Latency per request is milliseconds rather than microseconds. And no operating
system will boot from it or run a database on it.
