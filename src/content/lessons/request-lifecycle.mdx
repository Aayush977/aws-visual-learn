path of a single request. This is the reference architecture that turns up, in some
form, in most Solutions Architect scenario questions.

## Hop 1 — Route 53 turns a name into an address

Every request starts with DNS. **Amazon Route 53** is AWS's DNS service, and the "53"
is the port DNS runs on. It is a global service answered from edge locations, so a
lookup from Sydney is not served out of Virginia.

The two features worth knowing:

- **Routing policies** decide *which* address to return. Simple, weighted (send 10% of
  traffic to a new version), latency-based (send users to the fastest Region for them),
  failover (return the backup only when the primary fails a health check), and
  geolocation (return different answers per country).
- **Health checks** let Route 53 stop returning an address that is not responding —
  this is how DNS-level failover between Regions works.

<Callout type="exam">
When a question involves failing over **between Regions**, the answer usually involves
Route 53. When it involves distributing traffic **inside** a Region, the answer is a
load balancer. Route 53 is the only one of the two that can move traffic across Regions.
</Callout>

## Hop 2 — CloudFront serves what it can from the edge

**CloudFront** is the CDN. It keeps copies of your content at hundreds of edge locations
and serves them from whichever one is closest to the user.

Two consequences that matter more than they first appear:

1. **Latency drops** because the physical distance drops. Nothing you configure in your
   application beats not crossing an ocean.
2. **Load on your origin drops**, often dramatically, because cached requests never
   reach it. A CDN in front of a small server can absorb a traffic spike that would
   otherwise flatten it.

CloudFront is also where **AWS WAF** and **AWS Shield** attach, which is why "protect a
web application from a DDoS attack" points at CloudFront rather than at anything in
your VPC.

<Callout type="gotcha">
CloudFront is not only for static files. It can sit in front of a dynamic application
and still help — it terminates TLS at the edge and carries the request to your origin
over AWS's own optimised network, which is faster than the public internet even when
nothing is cached.
</Callout>

## Hop 3 — The load balancer picks a healthy target

An **Application Load Balancer (ALB)** receives the request and forwards it to one of
your instances. Three things it does that are easy to undervalue:

- **Health checks.** It polls each target and quietly stops sending traffic to any that
  fails. A broken instance produces no errors for users.
- **Cross-AZ distribution.** It has a presence in each AZ you enable and spreads traffic
  across all of them. This is the mechanism that makes multi-AZ actually work.
- **It is the only public thing.** The ALB sits in public subnets; everything behind it
  does not need a public IP at all.

Which load balancer to use is a standard exam question:

| Load balancer | Operates at | Reach for it when |
| --- | --- | --- |
| **Application (ALB)** | Layer 7 — HTTP/HTTPS | You need routing by path or hostname, or you are running containers |
| **Network (NLB)** | Layer 4 — TCP/UDP/TLS | You need extreme throughput, ultra-low latency, or a static IP |
| **Gateway (GWLB)** | Layer 3 | You are inserting third-party virtual firewalls or inspection appliances |

## Hop 4 — The instances sit in private subnets

The EC2 instances have **no public IP address**. They cannot be reached from the
internet, and a port scan of your public address range will not find them. The load
balancer forwards traffic to them over the VPC's private network.

If those instances need to make *outbound* calls — to fetch OS updates, or to call a
third-party API — they go through a **NAT Gateway** in a public subnet. Outbound works;
inbound does not. That asymmetry is the entire point.

<Callout type="exam">
"Instances must be able to download patches from the internet but must not be reachable
from it" is a NAT Gateway question, every time. And a NAT Gateway lives in **one AZ** —
for a highly available design you need one per AZ, or an AZ failure takes the other
zone's outbound traffic with it.
</Callout>

## Hop 5 — The database, in one place, replicated

Both instances talk to the same **RDS** database. With **Multi-AZ** enabled, RDS keeps a
standby copy in a second Availability Zone, replicates to it synchronously, and fails
over automatically — the endpoint name stays the same and DNS is repointed for you.

Two things Multi-AZ is *not*:

- It is **not** a way to scale reads. The standby serves no traffic. If you need to
  scale reads, that is a **read replica**, which is a different feature (asynchronous,
  and it *can* serve reads).
- It is **not** a backup. It replicates your mistakes faithfully. Deleting a table on
  the primary deletes it on the standby moments later. Backups and point-in-time
  recovery are what protect you from that.

<Callout type="gotcha">
**Multi-AZ = availability. Read replica = performance. Backup = recovery.** Three
different features solving three different problems, and swapping them is one of the
most common wrong answers on the SAA exam.
</Callout>

scenario questions are constructed.
