## The first report of the morning

Meridian's customers pull a dashboard report each morning. It is a Lambda function: read some
data, do some arithmetic, return some JSON. It had been live for months and nobody had thought
about it once.

Then a customer complained that the mornings felt slow.

The engineer who picked it up did the sensible thing and measured. The 09:00 report took
**8.1 seconds**. The 09:03 report took **190 milliseconds**. The 09:04 report took 180. The
11:40 report, after a quiet hour, took 7.6 seconds again.

Same function. Same customer. Same query, against the same data, returning the same number of
rows. A factor of forty, correlated with nothing except how long it had been since anybody
last asked.

So they optimised the query. Then they added an index. Then they cached the result. The fast
requests got slightly faster. **The slow ones stayed exactly as slow**, because none of the
three weeks of work touched the thing that was actually taking the eight seconds — which was
not their code running, but their code *arriving*.

## There is a server. You just do not own it.

"Serverless" is a billing and operations promise, not a physics claim. Your code runs on a
machine. What you are excused from is choosing it, patching it, scaling it and paying for it
while it idles.

What you get instead is an **execution environment**: a small sandbox that AWS creates for your
function, keeps around for a while, and eventually throws away. Everything strange about
Lambda — cold starts, the variable that mysteriously persists, the concurrency limits — comes
from that environment's lifecycle.

## What a cold start is actually made of

Four things, roughly in order of how much they usually cost:

1. **Your initialisation code.** Imports, framework bootstrapping, reading secrets, building
   clients. Usually the biggest slice and the one entirely within your control.
2. **Package size.** Everything in the deployment package is downloaded. A bundle carrying
   unused dependencies is paying for them on every cold start.
3. **Runtime.** Interpreted runtimes generally start faster than ones that have to warm a
   virtual machine first.
4. **Networking setup** when the function is attached to a VPC.

What is *not* in the list is your handler's logic — which is what Meridian spent three weeks
on.

### The one you exploit deliberately

Because init runs once per environment and the environment is reused, **anything you set up
outside the handler is shared by every subsequent invocation on that environment.** That is
the single most useful performance trick in Lambda:

```js
// Outside the handler — runs once per environment, reused by every invocation.
const db = new DatabaseClient({ endpoint: process.env.DB_ENDPOINT });

export const handler = async (event) => {
  // Inside — runs on every invocation. Keep it to the actual work.
  return db.query(event.customerId);
};
```

Move the connection, the SDK client and the configuration read *outside*. Warm invocations then
skip all of it.

<Callout type="gotcha">
The same reuse is a genuine source of bugs. A variable outside the handler <strong>persists
between invocations</strong>, so a counter, a cache or a half-written buffer left there leaks
one customer's request into the next one's. It is also non-deterministic: it happens only when
the environment is reused, so it passes every test and fails in production. Outside the handler
is for things that are <em>safe to share</em> — clients and configuration, never request data.
Files written to <code>/tmp</code> survive the same way.
</Callout>

### Fixing cold starts, in order of how lazy you can be

- **Trim the package.** Free, and helps every cold start.
- **Move work out of the handler** into init — or, better, delete it.
- **Provisioned concurrency** keeps a set number of environments initialised and waiting, so
  requests never meet a cold start. It costs money whether or not they are used, which makes it
  the answer when *latency is a requirement* rather than an annoyance.
- **Do nothing.** For an asynchronous job — a nightly batch, a file landing in S3 — an extra
  second before it starts is genuinely irrelevant. Cold starts matter when a human is waiting.

<Callout type="exam">
"A serverless API must respond with consistently low latency, including for the first request"
means <strong>provisioned concurrency</strong>. Warming functions by pinging them on a schedule
is a folk remedy that predates the feature and is offered as a distractor.
</Callout>

## Memory is a CPU dial

This one surprises everybody, and it is worth real money.

You configure a Lambda function's **memory**. What you are actually buying is a proportional
share of **CPU** — more memory means more CPU, and above a threshold, more cores. You are not
allowed to set them separately.

So a compute-bound function set to 128 MB can be *cheaper to run at 512 MB*: it gets several
times the CPU, finishes in a fraction of the time, and you are billed for duration. Paying four
times as much per millisecond for a fifth of the milliseconds is a saving.

**Measure, do not assume.** The relationship flattens — at some point more memory buys nothing
because the function is waiting on the network, not on CPU, and you are simply paying more.

<Callout type="cost">
The corollary: a function that spends its life waiting on an API call gains nothing from extra
memory, because CPU was never the constraint. Compute-bound functions scale with the dial;
IO-bound ones do not. Knowing which of the two you have is the whole optimisation.
</Callout>

## Concurrency: how it scales, and how it stops

**One execution environment serves one request at a time.** There is no threading model to
reason about — two simultaneous requests mean two environments.

**Concurrent executions** is simply how many are in flight at once. Traffic doubles, Lambda
creates more environments. That is the scaling story, and it is genuinely automatic.

It is not infinite. An account has a concurrency limit per Region — **1,000 by default**,
raisable on request — shared by *every function in that account*. Two controls carve it up:

- **Reserved concurrency** sets aside part of the pool for one function. It is a floor
  (nothing else can take it) and a ceiling (the function cannot exceed it). Use it to stop one
  runaway function starving everything else — and to protect a fragile downstream database from
  a thousand simultaneous connections.
- **Provisioned concurrency** is different in kind: it keeps environments *initialised and
  waiting*, which is about cold starts, not about limits.

When the limit is reached, further invocations are **throttled** — a `429`. What happens next
depends entirely on how the function was invoked, which is the next section and the part that
catches people out.

## Three ways a function gets invoked

The invocation model decides what happens to a request that fails or is throttled. It is the
most commonly missed detail in serverless design.

- **Synchronous** — API Gateway, an Application Load Balancer, a direct `Invoke`. The caller
  waits and receives the result. **A throttle or an error goes straight back to the caller**,
  and nothing retries unless the caller does.
- **Asynchronous** — S3 events, SNS, EventBridge. The event is queued by Lambda and the caller
  is told only that it was accepted. Lambda then **retries a failed invocation twice** before
  giving up, and a failed event can be routed to a **dead-letter queue** or an on-failure
  destination so it is not silently lost.
- **Event source mapping** — SQS, Kinesis, DynamoDB Streams. Here **Lambda polls the source**
  and calls your function with a batch. Failures return the messages to the queue; after enough
  attempts they go to the queue's dead-letter queue.

<Callout type="gotcha">
With SQS, set the queue's <strong>visibility timeout to at least six times the function
timeout</strong>. Too short, and the message becomes visible again while your function is still
processing it — so a second invocation picks up the same message and does the work twice. This
is the most common duplicate-processing bug in serverless, and it looks like a mysterious data
problem rather than a configuration one.
</Callout>

### Which means your function must tolerate duplicates

Every one of those models is **at-least-once**, not exactly-once. Retries exist, and a retry of
a function that already half-succeeded runs it again.

So a Lambda that charges a card, sends an email or increments a total must be **idempotent** —
safe to run twice with the same input. In practice: record the event's id before doing the
work, and return early if you have seen it. This is not a nicety; it is the price of a system
that retries on your behalf.

## API Gateway: the front door

Lambda has no address. Something has to accept an HTTP request and invoke it, and for an API
that is usually **Amazon API Gateway**.

It is a managed front door that does the work you would otherwise write yourself:

- **Routes** a method and path to a backend — a Lambda function, an HTTP endpoint, or an AWS
  service directly.
- **Stages** (`dev`, `prod`) are deployed versions of the same API, each with its own URL and
  settings — this is how a change is tested without touching production.
- **Authorizers** decide who may call: IAM, a Cognito user pool, or a **Lambda authorizer**
  running your own logic. Auth happens *before* your function is invoked, so rejected traffic
  never costs you an execution.
- **Throttling and usage plans** cap requests per caller, protecting both your function and
  your bill. With API keys, this is how you give different customers different rate limits.
- **Request validation** rejects malformed input at the gateway rather than inside your code.
- **Caching** can return a response without invoking the backend at all.

<Callout type="gotcha" title="29 seconds versus 15 minutes">
A Lambda function may run for <strong>15 minutes</strong>. An API Gateway integration waits
<strong>29 seconds</strong> by default and then returns a <code>504</code> — while your function
carries on running, and billing, invisible to the caller who has already given up.

Anything slower than a few seconds should not be answered synchronously at all. Accept the
request, return <code>202 Accepted</code> with an id, do the work asynchronously, and let the
caller poll or be notified. If a question describes a long-running job behind an API, that
pattern is the answer.
</Callout>

---

Meridian's eight seconds was not in their code. It was the environment being built around their
code, one request in every few hundred, at the exact moment a customer was watching.

They fixed it in an afternoon once they knew that: the SDK clients moved outside the handler,
the deployment package lost a dependency tree nobody had used since the first month, and the
function that a customer waits on got provisioned concurrency during business hours. The
09:00 report now takes 210 milliseconds.

Three weeks had gone into making the fast requests faster. The lesson is not that they were
careless — it is that **you cannot optimise a system whose shape you have not learned**, and
the shape of Lambda is an environment with a life of its own, which your code is only briefly
a guest in.
