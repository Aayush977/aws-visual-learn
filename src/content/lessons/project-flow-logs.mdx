## The problem

Project 7 ended on a claim: traffic going to S3 through a NAT gateway is money thrown away,
because a gateway endpoint carries it free.

That is easy to say and surprisingly hard to act on, because of a question nobody in a large
organisation can usually answer: **which of our forty VPCs is actually doing it?**

Brightwell's NAT gateway charges were four figures a month across the estate. Everyone agreed
some of it was avoidable. Nobody could point at a specific VPC and say *that one*, because a
NAT gateway bill is a single number — hours plus gigabytes processed — with no breakdown of
where the gigabytes were going.

Guessing is expensive in both directions. Add endpoints everywhere and you have created work
and clutter for VPCs that never needed them; add none and you keep paying.

The information exists. AWS can write down every network flow in the VPC, and once those records
are in S3 you already know how to query them — Project 5 built exactly that machinery.

## What a flow log record actually contains

Worth knowing, because the fields decide what questions you can ask:

| Field | What it gives you |
| --- | --- |
| `srcaddr` · `dstaddr` | Who talked to whom — the basis of "was this bound for S3?" |
| `srcport` · `dstport` | Which service. Port 443 for anything AWS-facing |
| `bytes` · `packets` | **The volume, which is what you are billed on** |
| `action` | `ACCEPT` or `REJECT` — rejects are how you debug security groups and NACLs |
| `interface-id` | Which ENI, so you can trace a flow to an instance or a NAT gateway |
| `start` · `end` | Time window, for partitioning and trend analysis |

The `bytes` column is the one doing the work here. NAT gateways are billed per gigabyte
processed, so summing bytes for flows that crossed a NAT and were destined for S3 gives you a
number you can put next to a line on the invoice.

<Callout type="gotcha" title="Flow logs record IP addresses, not service names">
There is no `service = S3` column. Flow logs are network records, so S3 appears as a destination
IP address in one of AWS's published ranges.

That means matching against the <strong>AWS IP ranges JSON</strong> that AWS publishes, filtered
to the S3 service and your Region. It is the fiddly part of the lab and the reason people
assume this analysis is harder than it is — it is not conceptually hard, it just needs a join
against a list.
</Callout>

## Why Athena rather than CloudWatch Logs Insights

Both can query logs, and the site's *Easily Confused* page draws the general distinction. Here
the choice is decided by two specifics:

**Volume and cost.** Flow logs across a large estate are enormous. Storing them in CloudWatch
Logs is considerably more expensive per gigabyte than S3, and this is data you query
occasionally, not constantly — the exact profile Athena is built for.

**Joins.** The analysis needs to join flow records against the AWS IP range list, and against an
account-name mapping so the output says "payments-prod" instead of an account number. That is
ordinary SQL in Athena and awkward in Logs Insights, which is built for filtering and
aggregating a stream rather than joining datasets.

<Callout type="cost" title="Partition the flow logs, or the analysis costs more than the finding">
Athena bills roughly <strong>$5 per terabyte scanned</strong>, and flow logs are one of the
largest datasets most organisations have. An unpartitioned <code>SELECT *</code> across a year
of them can cost more than the NAT charges you are trying to remove — which would be an
embarrassing way to end a cost-optimisation exercise.

Partition by date and account, and query one month at a time. This is the same lesson as
Project 5, and this is where it bites hardest.
</Callout>

The reason this project belongs in a Solutions Architect path rather than a billing one is the
shape of the reasoning, which recurs constantly at this level.

Nobody was arguing about whether gateway endpoints are good. Everybody already knew. The blocker
was that **the fix was cheap and the targeting information was missing**, so the whole
improvement sat undone for a year — not for want of knowledge, but for want of evidence.

A large amount of architecture work is like this. The design change is usually the easy part.
Being able to prove which of forty environments needs it, with a number attached, is what
actually gets it done.
