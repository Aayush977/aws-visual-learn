## The three words, precisely

**A Region** is a named geographic area containing a cluster of Availability Zones.
Regions are fully isolated from one another by design: an outage in `us-east-1` does
not spread to `eu-west-2`, and data does not move between Regions unless you
explicitly set up replication.

**An Availability Zone (AZ)** is one or more discrete datacentres inside a Region,
each with independent power, cooling and physical security. AZs in a Region are
connected by high-bandwidth, low-latency private links. They are close enough for
synchronous replication and far enough apart that a single fire, flood or power
failure hits only one.

**An Edge Location** is a much smaller site — there are hundreds of them, in far more
cities than there are Regions. Edge Locations run CloudFront (content caching),
Route 53 (DNS) and AWS Global Accelerator. They exist to shorten the physical
distance between a user and the first AWS machine that answers them.

<Callout type="analogy">
A Region is **a city**. An Availability Zone is **a building in that city with its own
generator**. An Edge Location is **a corner shop near your house** — it does not stock
everything, but what it does stock, you get in seconds instead of driving into town.
</Callout>

## Why the split exists

If AWS had built one enormous datacentre per Region, a single power failure would take
down every customer in that Region at once. Splitting a Region into independent zones
means you can run the same application in two or three of them, and survive losing one.

That is the whole idea behind the phrase **high availability**, and it is why
almost every "how do I make this resilient?" answer on the exam involves the words
*across multiple Availability Zones*.

## Choosing a Region

Four things decide it, and the exam tests all four:

| Factor | The question you are really asking |
| --- | --- |
| **Compliance** | Does the law require this data to stay inside a country or bloc? This one overrides everything else. |
| **Latency** | How far are my users from this Region? Distance is physics — you cannot configure it away. |
| **Service availability** | New services launch in a handful of Regions first. Not everything is everywhere. |
| **Cost** | The same instance costs different amounts in different Regions. `us-east-1` is usually cheapest. |

## Multi-AZ vs Multi-Region

These sound similar and get confused constantly. They solve different problems.

| | Multi-AZ | Multi-Region |
| --- | --- | --- |
| **Solves** | One datacentre fails | An entire Region fails, or users are on another continent |
| **Distance** | Tens of kilometres | Thousands of kilometres |
| **Replication** | Can be synchronous | Almost always asynchronous |
| **Typical cost** | Modest — often just a second instance | High — a duplicate of your stack |
| **The phrase that signals it** | "highly available", "fault tolerant" | "disaster recovery", "global users", "data residency" |

<Callout type="gotcha">
Multi-AZ is **high availability**. Multi-Region is **disaster recovery**. If an exam
question says a workload must survive the loss of a datacentre, the answer is multiple
AZs — reaching for multiple Regions is over-engineering, and the cheaper correct answer
is usually the one being tested.
</Callout>

<Scenario
  who="A UK council running a permit-application portal"
  problem="The portal runs on one server in one datacentre. When that datacentre lost power for four hours last winter, residents could not file anything, and the data must legally stay in the UK."
  solution="Keep everything in eu-west-2 (London) to satisfy data residency, but run the application on instances in eu-west-2a, 2b and 2c behind a load balancer, with a Multi-AZ database."
  outcome="Survives losing a whole datacentre with no data leaving the UK — and no second Region to pay for."
>
Note what this scenario does *not* need: a second Region. The requirement was
"survive a datacentre failure", not "survive losing London". Multi-Region would cost
several times more and would push data outside the UK, breaking the actual constraint.
</Scenario>

## Things that are global, not regional

A few AWS services are not tied to a Region at all. These come up as trick answers:

- **IAM** — users, groups, roles and policies are global.
- **Route 53** — DNS, served from Edge Locations worldwide.
- **CloudFront** — the CDN itself is global (though its origins are regional).
- **AWS WAF** and **Shield** — attached at the edge.
- **S3** — the *service* is global and bucket names are globally unique, but every
  bucket lives in one Region you choose. This distinction is a favourite exam trap.
