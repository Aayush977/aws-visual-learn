For thirty years "the database" meant one thing: a relational database, and you bent your
problem until it fitted. AWS takes the opposite position — **purpose-built databases** — and
offers a different engine for each shape of question.

That is genuinely better, and it is also why the exam can ask a database question that has
four plausible-looking answers. The way through is to stop thinking about the data and start
thinking about **the query you will run ten thousand times a second**.

## Relational — Amazon RDS and Aurora

**RDS** runs the databases you already know — PostgreSQL, MySQL, MariaDB, Oracle, SQL Server —
and takes the operational work off you: patching, backups, failover, replication. You still
tune queries and design the schema. You no longer install anything.

Use it when the data has a **fixed shape** and questions **join across** it, and when a
transaction must either fully happen or fully not happen. Orders and payments, bookings,
anything where "roughly right" is not acceptable.

Three RDS features that carry most of the exam weight, and are constantly confused:

| Feature | What it is for | What it is **not** for |
| --- | --- | --- |
| **Multi-AZ** | Availability. A synchronous standby in another AZ, automatic failover, same endpoint | Not for scaling reads — the standby serves no traffic |
| **Read replicas** | Performance. Asynchronous copies that serve read queries | Not automatic failover (though one can be promoted manually) |
| **Automated backups & snapshots** | Recovery. Point-in-time restore, typically to any second in the last 35 days | Not availability — restoring takes minutes to hours |

**Amazon Aurora** is AWS's own reimplementation of MySQL and PostgreSQL, wire-compatible with
both. It stores data in a shared, self-healing layer replicated **six ways across three
Availability Zones**, is markedly faster than standard RDS, supports up to 15 read replicas
with very low replica lag, and grows storage automatically to 128 TB. **Aurora Serverless v2**
scales capacity up and down with load, which suits spiky or unpredictable workloads.

<Callout type="gotcha">
Say it until it is automatic: <strong>Multi-AZ is availability. Read replicas are performance.
Backups are recovery.</strong> Three separate features solving three separate problems. Swapping
them is the single most common wrong answer in the database section of the SAA exam.
</Callout>

## Key-value — Amazon DynamoDB

**DynamoDB** is a managed NoSQL key-value and document store. There is no server, no version
to upgrade, and no capacity to plan if you choose on-demand mode. It returns single-digit
millisecond responses at effectively any scale, and stays there whether the table holds a
thousand items or a hundred billion.

What you give up is the ability to ask arbitrary questions. You design a DynamoDB table around
**the access patterns you already know** — get an item by key, or query a range within one
partition. There is no efficient equivalent of "join these two tables and filter on a column I
never indexed".

Worth knowing by name:

- **DynamoDB Accelerator (DAX)** — an in-memory cache built for DynamoDB, taking responses from
  milliseconds to **microseconds**, with no application changes.
- **Global Tables** — an active-active copy of your table in several Regions, so users on other
  continents read and write locally.
- **On-demand capacity mode** — pay per request, no capacity planning. The right default for
  unpredictable traffic; provisioned mode is cheaper for steady, well-understood load.
- **TTL** — set an expiry timestamp per item and DynamoDB deletes it for free. The tidy way to
  hold sessions or short-lived data.

<Callout type="exam">
The words that point at DynamoDB: <strong>"millions of requests per second", "single-digit
millisecond latency", "serverless", "flexible schema", "key-value", "no database management".</strong>
The words that point away from it: <strong>"complex joins", "ad-hoc queries", "existing SQL
application", "strong relational integrity".</strong>
</Callout>

## In-memory — Amazon ElastiCache

**ElastiCache** keeps data in RAM, so reads come back in microseconds. It is not usually where
the truth lives — it sits **in front of** a database and answers the questions that keep being
asked, so the database never sees them.

Two engines, and choosing between them is a standard question:

- **Redis** — richer. Persistence, replication, Multi-AZ with automatic failover, sorted sets,
  pub/sub, geospatial queries. Choose it when the cache must survive a restart, or when you
  need leaderboards, session stores or queues.
- **Memcached** — simpler. Pure in-memory cache, multi-threaded, easy to scale horizontally, no
  persistence and no replication. Choose it when you only want a big, fast, disposable cache.

## Analytics — Amazon Redshift, and friends

A production database is optimised to fetch a few rows very quickly. Asking it to scan five
years of orders and total them by region will work once, and will bring the website down if
an analyst does it at lunchtime.

**Amazon Redshift** is a data warehouse: columnar storage, massively parallel processing,
built for enormous aggregate queries over historical data. You load data into it from S3 and
run SQL against it, and it is where business-intelligence tools point.

Near it in most exam questions:

- **Amazon Athena** — SQL directly against files sitting in S3, **serverless**, priced per
  terabyte scanned. Ideal for occasional queries where standing up a warehouse is overkill.
- **AWS Glue** — the managed ETL service that catalogues and transforms the data on the way in.
- **Amazon QuickSight** — the dashboards people actually look at.

<Callout type="cost">
Athena versus Redshift is usually a question about <em>frequency</em>. Occasional queries over
data already in S3 → <strong>Athena</strong>, because you pay only for the scans. Constant
querying by many analysts all day → <strong>Redshift</strong>, because per-query pricing stops
being a bargain and dedicated compute wins.
</Callout>

## The purpose-built ones

You need to recognise these by their giveaway phrase, not to know them deeply:

| Service | Reach for it when the question says |
| --- | --- |
| **Amazon Neptune** | Graph. "Relationships between entities", social networks, fraud rings, recommendations |
| **Amazon OpenSearch Service** | "Full-text search", log analytics, operational dashboards |
| **Amazon DocumentDB** | "MongoDB-compatible" document database |
| **Amazon Keyspaces** | "Apache Cassandra-compatible" |
| **Amazon Timestream** | Time-series — IoT sensor readings, metrics over time |
| **Amazon QLDB** | An immutable, cryptographically verifiable ledger of every change |

<Scenario
  who="A food delivery app in three cities"
  problem="Everything lives in one large PostgreSQL instance. Looking up a restaurant's menu — the single most frequent query in the system — competes with order processing. The analytics team's nightly revenue report locks tables for twenty minutes. At 7pm on Fridays the database CPU pins at 100% and orders start failing."
  solution="Orders and payments stay in RDS PostgreSQL, Multi-AZ, because they need real transactions. Menus and restaurant profiles move to DynamoDB, fetched by restaurant ID.   outcome="The Friday peak no longer touches the relational database for reads at all. The analysts stopped affecting production entirely, and the RDS instance was downsized twice."
>
Four data stores where there was one, and each choice is traceable to a *question* rather than
to a preference. This shape — relational for the truth, key-value for the hot path, cache in
front, analytics off to the side — is one of the most common real architectures on AWS.
</Scenario>
